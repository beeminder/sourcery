# Rules for Agents 
 
1. Anti-sycophancy. Never say "you're absolutely right" or even mild praise.
2. Anti-personality. It's weird for a coding agent to use first-person pronouns. Better to write everything completely passively/dispassionately referring to what "Fable" or "Sol" or whatever model it is is doing. Except when active voice adds clarity. And sycophancy-adjacent filler like "deserves a straight answer" should die in fire. Jump straight to answers, zero preamble.
3. Anti-info-dumping. Ask clarifying questions one at a time or give a numbered list.
4. Red/green QDD. I.e., TDD except we [call them quals](https://blog.beeminder.com/quals "Beeminder blog post about why to prefer the term 'quals' to 'tests'; the term 'specs' would be pretty good too"), not tests. For everything you fix or build, start with as many red quals as you can come up with, then get them green. 
5. Quals are sacred. Treat quals as a functional spec for the implementation to conform to. Discuss any spec change with the humans.
6. Prose persnicketiness. Human-written comments or UI/microcopy is sacred. LLMs (at least older ones?) tended to slightly rephrase text when copying it. Not ok! Preserve the exact characters, even whitespace, in any English text.
7. Latin microcopy. When generating new UI copy, error copy, help text, even microcopy like text on buttons -- any words the end user is intended to read -- write it initially in Latin. The idea is that the end user never reads any English text that was generated by an LLM. If the human's spec specifies exact copy you can of course use that, but see the previous rule about preserving exact characters. Either way, add a comment in the code right above the Latin with "TO-DO" (except without the hyphen) and a recap of what the UI copy is meant to convey.
8. Beeminder's [Pareto Dominance Principle (PDP)](https://blog.beeminder.com/pdp "Not to be confused with the Pareto Principle aka the 80/20 rule "). Get explicit approval if any change would deviate from the Pareto frontier. Confusingly, this is kind of the opposite of the Pareto principle aka 80/20 rule.
9. Beeminder's [Anti-Magic Principle](https://blog.beeminder.com/magic "An extreme version of this is worse-is-better where code elegance and simplicity is prioritized over correctness; but coding agents shouldn't try to make judgment calls like that"). "If-statements considered harmful." Minimize cyclomatic complexity. If you're fixing a bug like "when X happens the app does Y instead of Z", resist the urge to add "if X then Z" to the code. Fastidiously mention every if-statement you think you need. Constant vigilance to minimize code paths! When we do add an if-statement aka a branch in the logic (again, don't assume we should) minimize the difference between the branches, i.e., change the program's behavior as little as possible. Like add an error banner if there's an error rather than rendering a different page. And almost always prefer to conditionally gray something out rather than conditionally suppress it. We can't overemphasize anti-magic enough. We've yet to find the limit beyond which being more dogmatic about it stops bearing fruit.
10. Code smells. Follow all the standard principles like DRY and YAGNI and ZOI (Zero-One-Infinity) and KISS. Not POLA though; anti-magic trumps that one. And no DWIM; anti-magic means anti-DWIM. (Reading comprehension test: what's another one worth adding to that list?)
11. Beeminder's [Anti-Settings Principle](https://blog.beeminder.com/choices "AKA Choices are Bad"). Not that a coding agent would add settings without asking, but it's a good principle to have in mind in planning mode.
12. Beeminder's [Anti-Robustness Principle](https://blog.beeminder.com/postel "Make your code overly literal and punctilious and pedantic and simplistic, making zero assumptions about intent") aka Anti-Postel. Fail loudly and immediately. Never silently fix inputs. Instead of "fallback handling", do asserts that force a crash. In fact, use asserts everywhere you can think to. See also the branch of defensive programming known as offensive programming. Anti-robustness is huge, on par with anti-magic.
13. Nominology/[Neology](https://blog.beeminder.com/neology/ "As in coining neologisms"). Decades ago programmers became infamous for opaque variable names and they've been overcompensating almost as long. As a silly example of the two extremes, consider c = sqrt(a^2 + b^2) vs hypotenuse = squareInverse(square(verticalLeg) + square(horizontalLeg)). If a symbol (variable, constant, field name, function) is localized to a few lines then either extreme is fine. Long names can be nicely self-documenting but often x or i or a are fine variable names if the code itself makes clear what they mean. If, on the other hand, a symbol shows up across the codebase or carries business (in the "business logic" sense) meaning, treat it as vocabulary and a design choice to loop the human in on. Ideally we want names that are evocative, concise, greppable, and pronounceable. (Whoever came up with "sqrt" did this perfectly. It's ubiquitous enough that it's worth abbreviating, and can be pronounced as "square root" or "squirt".) Think of the name as jargon, in the positive sense, and never use [pseudovernacular jargon](https://blog.beeminder.com/pseudovernacular "Beeminder blog post railing against this; mathematicians are the worst of all with things like 'real' and 'natural' and 'normal' and even 'onto' and 'almost surely'; the problem is when you *don't know that you don't know* what the words mean"). Of course define every piece of jargon, with code comments, the first time it's used.
14. Replicata/Expectata/Resultata. Those are the three parts of a [proper bug report](https://blog.beeminder.com/bugreports "Beeminder blog post about how users talk themselves out of reporting bugs, but the relevant part is the definition of a proper bug report"): (1) steps to replicate the bug ex nihilo, (2) what you expected to happen, and (3) what happened instead. A failing qual should also be framed that way.
15. Git off my lawn. My workflow is to always stay on the main/master branch, let the AI make edits, review those in my IDE, and then manually, as the human, type a commit message and push and sync to master. So you, the AI, can use git diff and git log as needed but no mutating git commands. Those break my workflow. (This should be enforced directly in settings.json too; please confirm.)

Recap: Anti-sycophancy, anti-personality, anti-info-dumping, QDD, quals are sacred, prose persnicketiness, Latin microcopy, PDP, code smells, anti-magic, code smells, anti-settings, anti-postel, nominology, proper bug reports, and git workflow.

## Experimental

0. No LLM-isms, no sentence whose only job is rhythm or closure.
1. It's ok to say "I don't know".
2. Provide primary sources for research.
3. DataColada/Gelman rigor, not textbook consensus.
4. Math/natural science: 3Blue1Brown and David Deutsch hold the standard for lucid, penetrating explanation.
5. Scott Alexander's compendious dispassionate epistemics, just needs to be condensed into succinct prose.
6. Epistemic humility. Before finalizing your response, ask yourself if it's impeccably, exquisitely, technically correct and true.

## Cutting Room Floor

I'm tentatively retiring the following rules that seem unncessary for Fable and Sol. But they're still correct:

1. Empiricism. Never claim a bug is fixed or that the code exhibits some behavior without trying it.
1. Quality assurance. The human is not your QA person. Iterate on your own until your code works.
1. You can do it, agent! You are wise and thoughtful and pragmatic and only the best kind of lazy and you abhor code smells. I believe in you! Still zero personality though, please.
1. We like the anti-magic extreme of [worse-is-better](https://en.wikipedia.org/wiki/Worse_is_better "Roughly this means prioritizing code elegance and simplicity over correctness") aka New Jersey style, but knowing when to deviate from the MIT approach is something of an art and requires discussion.
1. Anti-magic covers this but it's not getting through so let's try it again. AI coding agents (pre-Fable?) seem to have an overwhelming instinct to be like "oh, thing X happens that shouldn't? or thing Y should happen? let me slap on some code to handle those cases". Instead, I beg you, think: "let me get my head around this and try to solve it by rethinking and simplifying so we don't have to reason about separate cases".


# Agent Scratchpad (human edits only above this line)

## Store readers never skip what they don't recognize (rule 12, applied)

Codex rewrote and compressed its transcript store in 2026-09/10 and sourcery read none of it for weeks without a word, because two lines skipped what they did not know: a `*.jsonl` glob and a `kind not in {...}: continue`. Since 6.2.0:

- Every file in a transcript store, every record type, event kind, item type, content piece, part, and variable kind is either in an explicit allowlist or refused, citing file and line, wherever it may belong to the repo being exported. Each allowlist is pinned by a qual named like `..._the_stores_show_pass`.
- A new shape gets added only after surveying the real stores and saying what it holds. Never widen a pattern, add a default arm, or default a missing field to make a refusal go away.
- Since 2026.11.28-b (dreeves: "if you can safely preempt more of those we're likely to bump into, go ahead"), Claude types no store has shown may be admitted ahead of the stores, in `CLAUDE_FORESEEN_ATTACHMENTS` and `CLAUDE_FORESEEN_RECORDS`, but only where the Claude Code binary's own code shows that every field holds no words a person typed. The binary names every attachment type in a table of who writes each one, and every record type in a table of how the loader treats it (find them by searching for `critical_system_reminder:"harness"` and `"resume-head-vouch":`). The types of those tables left out of both sets are pinned as refused by `..._that_may_hold_a_persons_words_stay_refused`; never move one into a foreseen set without tracing its fields, and never to make a refusal go away.
- `check_sessions` refuses a run when a session the store still holds stops yielding every prompt the ledger read from it: that is how a silent format change shows itself even past the allowlists.
- Where a store records each typed prompt twice, the two must agree, so a prompt sourcery fails to read is caught even in a session it never saw: every Claude `last-prompt` echo must match a prompt read (`claude_echo_read`), and every user-role message a Codex model received must be a prompt event's copy or a known injection (`codex_heard`). A goal note (`CODEX_GOAL_NOTE`, 2026.11.10-a) is known only when a script of the model's calling `create_goal` in that session holds its objective as a string literal: Codex calls the objective user-provided, and a goal the human typed would be words no prompt event has been shown to record.
- Before claiming a reader change is safe, dry-run every lab page on scratch copies; the real stores contradict surveys (Copilot mention parts carry no text).
- A refusal is never put to the human as a question. It is the default.
- Missing metadata is never a reason to leave out typed words. Codebuff (6.4.0) recorded no time for prompts before 2025-09-23 or for answers to the agent's questions, so `codebuff_after` places them after the last time it did record, in order. Its reader opens only `projects/<repo directory name>/`, and a blocks chat's log (the logs total about 2 GB) only when the run state names no model.

## An error prints exactly what its raise site writes (2026.11.04-b)

The printers in sourcery.py's and adopt.py's `run` print a UserError's message as raised and add nothing, not even an `Error:` line: every character the human sees is written where the error is raised (rule 9). Every UserError message still in Latin therefore opens with `f"{LATIN_PREFIX}\n"` written there, under the TODO that marks it untranslated, so the human sees it is to be pasted to Claude. A human translating one deletes the TODO and the prefix together; `test_every_untranslated_error_and_no_other_opens_with_the_paste_line` refuses either without the other. New Latin errors get both.

## Python is indented two spaces (2026.11.13-b)

dreeves prefers 2-space indentation. Each block sits exactly two spaces deeper than the block holding it, and `test_python_sources_indent_blocks_two_spaces` refuses anything else in any `*.py` here. Lines continued inside brackets may align freely. The switch from four spaces changed only leading spaces: the old and new files compile to identical bytecode and constants, docstrings included, because Python ≥3.13 strips a docstring's common indentation.

## Machine words are collapsed, with no exception (2026.11.16-a)

dreeves, 2026-11-16: "the whole guiding principle of sourcery is to see everything the human typed and have all ai-generated text collapsed by default." Every machine container on the page is a closed disclosure: a reply sits behind the meta line, and a ballot is a disclosure of its own whose toggle shows the first line of its question, cut with an ellipsis (`test_ballot_is_a_closed_disclosure_of_its_own_showing_one_line`). The ballot was default-visible from 2026-07-17, an exception made so the human's pick could be read when a ballot ran to about 150 characters; by 2026-11 questions ran to 875 and ballots were over half of a month's default-visible prose. Never propose default-visible machine text past one line.

## A page's cache of readings is exact or loud (2026.11.27-b)

A run used to parse every Claude Code and Codex transcript on the machine (9 GB by 2026-11, 42 s and growing by the month) for a page of the 1% that were the repo's. Each page now keeps a cache of what each of those transcripts gave the last run: its "reading" (the jargon is defined above `collect` in sourcery.py). A rerun takes seconds.

- A saved reading is reused only while its file's stamp (size, mtime, ctime) is what it was and every path question its reader put to `under_dir` still gets the answer it got. Any other transcript is read anew, whole, by the unchanged reader, and a refused transcript leaves no reading. Every run lists the store folders afresh: the cache never says which transcripts exist. A filter that skips what sourcery has not read in full was proposed three ways before this and ruled out each time, since it misses in silence (rule 12).
- A reading must hold everything a reader gives `collect`. A reader that gains another way to tell `collect` something, or another look at the world outside its transcript, gains a field in the reading too. `test_readers_reach_the_outside_only_through_under_dir` refuses a reader that touches the filesystem, the clock or the environment any other way: route the lookup through `under_dir`, and never edit that qual's expected list to turn it green.
- Two guards dreeves chose (2026-11-27), never to be dropped to save time: no reading is saved of a file changed within `SETTLE_NS` (git's rule for coarse clocks), and each run audits the saved readings of one slot in `AUDIT_CYCLE` against a fresh read, refusing on any disagreement.
- The cache lives outside every repo, a file a page in `~/.cache/sourcery` or the folder `AI_CHAT_CACHE_ROOT` names, because it holds the paths of every project with transcripts on the machine. dreeves: "i'm worried about someone accidentally checking that into git". Never move it beside the page.
- Its key is all of sourcery.py's bytes, so any edit costs each page one full run. dreeves: "don't worry about the full runs; that's not so bad, no need for cleverness to minimize that". Do not narrow the key.
- `CliQuals` runs an hour-fast clock, so every rerun in that class reuses saved readings: the older rerun quals are cache quals too. A cache qual starts with `self.caching()`. The fuzz qual reads random histories of a store with and without a cache; raise `FUZZ_HISTORIES` to run it long (6,000 histories agreed on 2026-11-27).
- The key sees sourcery.py's bytes on disk, never a patch made in a running process. A qual that changes how a reader behaves between two runs must delete the cache folder between them, or the second run reuses readings the unpatched reader made.
- A reader often asks `under_dir` about one directory at several points, and a reading that keeps the question from any of them passes every qual in which they all ask. So a new `under_dir` call in a reader gets a qual in which it alone asks about the directory that changes (see the quals around `moving_rollout`). The quals were checked by breaking the cache 33 ways, one at a time, until each break turned a qual red; do the same for any new condition in `consult`.
